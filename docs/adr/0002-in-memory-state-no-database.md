# 2. ไม่มีฐานข้อมูล — เก็บ state ในหน่วยความจำ, reconnect ด้วย session token

วันที่: 2026-05-29

## สถานะ

Accepted

## บริบท

ผู้ใช้ขอให้ "ถ้าเป็นไปได้ไม่ต้องมี database" เกมเป็นการเล่นสดกับเพื่อนในห้องที่สร้างชั่วคราว ไม่มีระบบสมัครสมาชิก ไม่ต้องเก็บประวัติข้ามวัน แต่เกมออนไลน์ย่อมเจอเหตุ "ผู้เล่นหลุดกลางเกม" ซึ่งเลือกไว้แล้วว่าให้ **จองที่ไว้ + auto-pass ระหว่างหาย + กลับมาต่อได้**

## การตัดสินใจ

เก็บ state ของทุกห้อง/เกมไว้ใน **หน่วยความจำของเซิร์ฟเวอร์** (in-memory store เช่น `Map<roomCode, GameState>`) ไม่ใช้ฐานข้อมูล

- identity ของผู้เล่น = ชื่อที่ตั้ง + **session token** ที่ client สร้างและเก็บใน `localStorage`
- เมื่อหลุดแล้วกลับเข้ามาด้วย room code + session token เดิม เซิร์ฟเวอร์ผูก socket ใหม่เข้ากับที่นั่งเดิมและส่ง state ปัจจุบันกลับไป
- ห้องที่ว่าง/จบแล้วถูกลบออกจาก memory ตาม timeout

## ผลที่ตามมา

- **ดี:** deploy ง่าย ไม่ต้องตั้ง/ดูแล DB, ไม่มีข้อมูลผู้ใช้ให้ต้องปกป้อง, ตรงกับลักษณะเกมเล่นสดชั่วคราว
- **เสีย / ข้อแลก:**
  - **เซิร์ฟเวอร์รีสตาร์ท = เกมที่กำลังเล่นหายทั้งหมด** ยอมรับได้สำหรับเล่นกันเล่นๆ แต่ต้องระวังตอน deploy (ไม่ deploy ทับเกมที่เล่นอยู่)
  - รันได้แค่ **อินสแตนซ์เดียว** (single process) — สเกลแนวนอนไม่ได้ถ้าไม่เพิ่ม shared store (เช่น Redis) ภายหลัง
  - session token อยู่ใน `localStorage` ถ้าผู้ใช้ล้าง storage หรือเปลี่ยนเครื่อง จะกลับเข้าที่นั่งเดิมไม่ได้
- ถ้าอนาคตต้องการความทนทาน (เล่นข้ามเซสชัน, สเกลหลายเซิร์ฟเวอร์, เก็บสถิติ) ต้องทบทวนการเพิ่ม persistence layer ซึ่งจะกลับมติฉบับนี้
